# 检索链路消融评测结果

> 首次运行：2026-08-30 ｜ 提交：v1.2（父子文档检索）之后
> 复现：`python -m backend.eval.run_eval`
> 环境：Ollama bge-m3（1024 维）+ bge-reranker-base（CPU/onnxruntime）+ ChromaDB
> 语料：14 个分块（单文档）｜ 问题集：28 条（`qa_dev.yaml`，人工标 gold）
> 参数：统一召回 20 条候选 → 取 top 5，rrf_k=60，MMR λ=0.7

## 总体结果

| 配置 | Hit@1 | Hit@3 | Hit@5 | MRR@5 | nDCG@5 | 平均延迟 |
|---|---|---|---|---|---|---|
| A 仅向量（similarity） | 0.821 | 0.929 | 0.929 | 0.869 | 0.825 | 254 ms |
| B 向量 + 精排 | 0.786 | **1.000** | **1.000** | 0.881 | **0.885** | 1645 ms |
| C MMR + 精排 | 0.786 | 1.000 | 1.000 | 0.881 | 0.885 | 1108 ms |
| D 双路 + RRF | 0.821 | 0.964 | 1.000 | **0.890** | 0.884 | **201 ms** |
| E 双路 + RRF + 精排 | 0.786 | 1.000 | 1.000 | 0.881 | 0.885 | 1111 ms |

## 分类别（Hit@1 / MRR@5）

| 类别 | n | A 仅向量 | B 向量+精排 | D 双路+RRF | E 完整链路 |
|---|---|---|---|---|---|
| keyword（字面重合高） | 10 | 0.80 / 0.85 | **0.90 / 0.95** | 0.80 / 0.88 | 0.90 / 0.95 |
| semantic（需语义理解） | 12 | 0.75 / 0.82 | 0.67 / 0.81 | **0.83 / 0.90** | 0.67 / 0.81 |
| cross_lingual（英文查中文档） | 3 | **1.00 / 1.00** | 0.67 / 0.83 | 0.67 / 0.75 | 0.67 / 0.83 |
| multi_topic（一线索多点） | 3 | 1.00 / 1.00 | 1.00 / 1.00 | 1.00 / 1.00 | 1.00 / 1.00 |

## 七条结论

### F1 当前实验设计不成立，召回阶段完全饱和
语料只有 14 个分块，而召回候选数设的是 20，**候选集恒等于全库**。后果有两个：
BM25 那一路没有补进任何向量漏掉的候选（无新料可补）；E 与 B 的结果**逐条完全相同**，
说明精排把融合带来的顺序信息全部覆盖掉了。

也就是说，这套配置目前只能区分"排序能力"，测不出混合检索最核心的价值"补召回"。
**下一件事不是调参，是把语料扩到 100+ 分块。**

### F2 单看性价比，D（双路 + RRF）是最优配置
MRR 全场最高（0.890），延迟全场最低（201 ms，比加精排快 5.5 倍）。
它把向量 top5 漏掉的 q09、q22 捞回命中区，并把 q14 从 Hit@1=0 抬到 1。

### F3 精排的收益是分查询类型的，不是全局的
keyword 类 Hit@1 从 0.80 → 0.90（MRR 0.85 → 0.95），提升明确；
semantic 类反而从 0.75 → 0.67。整体 nDCG@5 从 0.825 → 0.885 是真的，
但 Hit@1 掉了 3.5pp —— 精排的实际作用是**把对的块捞进前五，而不是把它们排到第一**。
具体翻转：q05 被抬进第 1，q16、q24 从第 1 掉出第 1（但仍在 top3 内）。

这条决定了上线策略：精排不是无条件增益，它换来的是"前五必有一条对的"，
代价是首条命中率和 1.4 秒延迟。

### F4 跨语种查询被精排明显拉低（样本仅 3 条，算观察不算结论）
A 1.00 → B 0.67。工作假设：bge-reranker-base 的训练语料以中文为主，
cross-encoder 的跨语种能力弱于 bge-m3 这种多语 embedding。
要证实得把 cross_lingual 扩到 30 条以上。**这是个值得测的方向，不是可下结论的数字。**

### F5 MMR 在当前规模下完全无效
B 与 C 各项指标一模一样。原因：`fetch_k=20 ≥ 语料总量 14`，
MMR 没有可 diversify 的余量，λ 只影响排序，而前 5 名本来就已经是全库候选。
MMR 的价值只在召回池远大于 top_k 时才可能出现，等语料上到千级再评估。

### F6 BM25 弱命中会污染 RRF（已定位，未修）
q25 查询是英文 `"the resume award part"`，文档全是中文，
A 的 Hit@1=1，开双路后 D 的 Hit@1=0 —— 被 BM25 挤下去了。
机制：RRF 只看名次不看分数强度，`1/(60+rank)`，
所以 BM25 只要把某个靠噪声 token 命中的块排进自己列表，就白得一票。
`bm25_service.search()` 目前只丢弃 `score <= 0`，没有相对阈值。

潜在修法：给 BM25 路加相对分数过滤（`score < top1_score * α` 丢弃），α 取 0.1~0.3 扫一遍。
**本次故意没改**：证据只有 3 条跨语种样本，对着 n=3 调阈值就是过拟合，
先把评测集扩起来再动这个参数。

### F7 父子文档（v1.2）这次测不到
当前库里 14 个块的 metadata 都没有 `parent_content`（是 recursive 策略入库的），
`_expand_to_parents()` 会原样返回，等于 no-op。
要评 v1.2 必须先用 `parent_child` 策略重新入库，再对比"子块命中→父块展开"与"直接用父块检索"。

## 端到端：固定管线 vs Agentic RAG

跑法：`python -m backend.eval.run_agent_eval --engine both --fresh`
（12 题：4 单跳对照 + 5 多跳 + 3 改写/跨语种；判分用人工 `must_contain` 关键词全覆盖，不用 LLM 当裁判）

### 逐题独立（`--fresh`，每题前清空对话历史）

| 引擎 | 全对率 | 关键词覆盖 | 平均延迟 | single | multi | rewrite |
|---|---|---|---|---|---|---|
| 固定管线 RAGChain | 0.417 | 0.575 | 8.1 s | 0.75 | 0.20 | 0.333 |
| AgentRAGChain | **0.667** | **0.778** | 33.0 s | 0.75 | **0.40** | **1.000** |

Agent 侧另外两个量：平均检索 1.0 次/题，未查库率 0.167，兜底回退率 0.0。

### 另一种条件（12 题共用一份对话历史，早期规则：有历史时允许不查库）

| 引擎 | 全对率 |
|---|---|
| 固定管线 | 0.667 |
| Agent | **0.167**（其中 83% 的题一次检索都没发生） |

### F8 Agent 的收益只在改写与多跳，单跳完全持平

single 类两边都是 0.75，Agent 多付 4 倍延迟没有换来任何提升。
也就是说"上 Agent"不是一个无条件升级，它是专门用来补检索层短板的：
措辞和原文不一致（rewrite）、答案散在多个分块（multi）这两类才值得开。

### F9 跨语种/换措辞提升最大（0.333 → 1.000），但功劳是"再查一次"

英文提问时固定管线经常召不回（见 F4），Agent 会用英文查一次、再用中文查一次，
第三次往往直接命中。这和检索层 F3 里"精排害了 semantic 类查询"是同一个缺口的两种补法 ——
精排是在已有的 20 个候选里挑，改写查询是去捞新的候选，后者才是混合召回没做到的那部分。

### F10 "允许复用历史"这条更聪明的规则，实测是灾难

早期实现是：本轮没查库但已有对话历史时，认它合理，不回退。
结果 Agent 全对率 0.167，比固定管线的 0.667 低一大截，83% 的题模型干脆不调工具，
直接凭上下文（甚至凭常识）作答，答案里还带着 `[1] [2]` 这种根本不存在的引用。
现在改成无条件回退：本轮没有检索证据 → 退回固定管线重答。
代价是 17% 的题白跑一轮 Agent（几秒），换来的是"答案不可能完全没有依据"。
在小模型上，纪律性约束比 prompt 里写"你必须先检索"可靠得多。

### F11 同一引擎换一种条件就差 3 题，绝对值不可引用

固定管线在"带历史"下 0.667、"逐题独立"下 0.417，差 3 题，纯粹来自对话历史带来的信息
以及 temperature 0.7 未固定种子的生成随机性。n=12 时这个量级完全在噪声内。
**这份评测里值得引用的只有同条件、同引擎的相对差**（fresh 下 Agent 在 multi/rewrite 两类各 +2、+2 题），
别把 0.667 这种数字当成"系统准确率"讲给面试官。

### F12 兜底路径一次都没触发，但模型倾向早停

`GraphRecursionError` 没出现（8 步上限够用），平均检索只有 1.0 次/题，
`max_search_calls=4` 是写在提示词里的软约束，模型基本查一次就收工。
a06（学校 + 游戏域名）、a09（两个音量参数 + 文件路径）这类题两边都答不全，
说明真正的瓶颈还是单次检索覆盖不够，而不是"Agent 不会多查" —— 让它多查的开关是提示词，不是步数上限。

### F13 上下文窗口被静默截断：Top K 调大反而全答错（已修）

现象：同一道三合一的题（毕业时间 + 部署计划 + 刷题目标），Top K=5 时答对两条；
把 Top K 拖到 18，三条反而全丢，模型还编出一个语料里根本没有的"部署地址 127.0.0.1:5000"。

原因：`ChatOllama` 没设 `num_ctx`，用的是 Ollama 服务端的默认窗口。提示词超出后从**头部**丢弃，
而检索资料就拼在 system 段里 —— 被丢掉的正是资料本身，模型看到的只剩问题文本。

同一份检索结果，只动窗口：

| 设置 | 上下文字符 | 结果 |
|---|---|---|
| 不设 num_ctx（服务端默认窗口） | 9003 | 三条全错，并编造部署地址 |
| num_ctx=8192 | 9003 | 三条全对，53.2 s |
| num_ctx=8192 + 预算 6000 字 | 5551（14 块留 9 块） | 三条全对，12.6 s |

修复：显式设 `llm.local.num_ctx: 8192`，再加一层 `retrieval.max_context_chars: 6000`，
按精排名次从后往前丢、至少保留 1 块；链路的 `{context}` 与前端的来源列表共用同一个
`_context_docs()`，保证"列给用户看的"就是"模型实际看到的"。公开的 `retrieve()` 不裁剪，
评测量的仍是检索本身。

对已有结论的影响：端到端 12 题跑的是默认 k=5（3126 字，没超默认窗口），F9~F12 不受这个 bug 影响。
但它解释了 multi 类为什么只有 0.20 —— 那道题在 k=8 就能三条全对（实测），
**瓶颈是单次检索的覆盖面，不是生成能力**。这条也印证了 F12。

## 评测侧下一步

1. 语料扩到 100+ 分块（多文档、含表格和长文），这是所有其他结论的前提
2. 加 F1 之后的重跑：此时才能证明 BM25 的补召回价值
3. 补 query 改写（condense question）与 multi-query 两种消融，目前都还没实现
4. 生成层指标（忠实度 / 答案相关性）需要固定 LLM 与裁判模型，另行设计
5. cross_lingual 类别扩到 30 条，验证 F4
6. 端到端问答集扩到 40 题并固定生成种子（或降温度到 0），否则 F11 那个量级的噪声会一直盖住真实差异
7. 给 Agent 加"必须至少检索一次"的结构化约束（工具选择用 constrained decoding），
   现在只能靠回退兜底，本质是事后补救而不是让它学会查

## 已知偏差声明

- 语料来自单一文档（本人的知识笔记），主题集中，查询区分度天然偏低
- gold 标注由项目作者本人完成，未做双人一致性校验
- 延迟为单机 CPU 冷启动后的均值，B 组含模型首次加载开销，组间不可直接比绝对值
- 样本量 28 条，0.05 以下的指标差异不具备统计意义
- 端到端问答集只有 12 题，生成温度 0.7 且未固定种子，同引擎换条件就能差 3 题（见 F11）
- 端到端延迟包含 qwen2.5:7b 本地生成的全部耗时，换 GPU 或换 API 后组间相对关系可能变化
